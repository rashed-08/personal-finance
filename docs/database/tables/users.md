# Users Table Specification

## Purpose

The `users` table stores application user identities for authentication and authorization.

A user is the person who logs into the application. Version 1 of the schema was single-user; this table introduces authenticated access while keeping financial data unscoped (single-user login gate). Multi-user data ownership is a future enhancement.

The Auth module owns this table.

# Responsibilities

- Store user identity (email, name)
- Store password hashes for local (email/password) login
- Store external identity links (Google Sign-In)
- Track email verification state
- Carry the user role for future role-based authorization

# Business Rules

- Email is the unique login identifier and compared case-insensitively.
- Passwords are stored only as BCrypt hashes; plaintext is never persisted (NFR-006).
- Google-only users have no password hash and cannot use email/password login.
- All new users receive the OWNER role; role checks are future-ready but not enforced in v0.11.

# Design Decisions

- UUID primary key, generated by the application (consistent with all other tables).
- Case-insensitive email uniqueness via a functional unique index instead of citext.
- `password_hash` is nullable so external-identity users need no local credential.
- Role stored as a plain column (no role/permission tables) — sufficient for the "future-ready" requirement of v0.11.
- Financial tables are intentionally NOT user-scoped in this version.
