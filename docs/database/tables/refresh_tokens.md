# Refresh Tokens Table Specification

## Purpose

The `refresh_tokens` table stores server-side state for JWT refresh tokens.

Access tokens are short-lived, stateless JWTs. Refresh tokens are long-lived, opaque random values delivered to the client as an httpOnly cookie. Each refresh token is stored hashed so a database leak does not expose usable tokens.

The Auth module owns this table. A row per issued token is the basis for session management: listing active sessions, rotation, and revocation.

# Responsibilities

- Persist issued refresh tokens (hashed)
- Enforce expiry
- Support rotation (old token revoked when a new one is issued)
- Support revocation (logout, password change)

# Lifecycle

↓

Use (rotate: revoke + issue replacement)

↓

Revoke (logout, password change) or Expire

Expired and revoked rows may be purged by a future cleanup job.

---

# Business Rules

- The raw token value is never stored — only its SHA-256 hash.
- A token is active when `revoked_at IS NULL` and `expires_at` is in the future.
- Refresh rotates the token: the presented token is revoked and a new one issued.
- Logout revokes the presented token.
- Changing the password revokes all of the user's active tokens (part 3 of the auth epic).

# Design Decisions

- Opaque random refresh tokens (256-bit) instead of JWT refresh tokens — trivially revocable server-side.
- SHA-256 (not BCrypt) hashing: the input is already high-entropy, and lookups must be by exact hash.
- `updated_at` is intentionally omitted — rows are immutable except for the single `revoked_at` transition.
- ON DELETE CASCADE so removing a user removes their sessions.
